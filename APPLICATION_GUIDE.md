# Outreach Flow — Comprehensive Application & Architecture Guide

This guide provides an end-to-end technical and operational reference for **Outreach Flow**. It is written so that any software engineer, technical lead, or stakeholder can understand the system's purpose, architectural data flow, user interface layout, database schemas, external integrations, current constraints, and future roadmap.

---

## 1. What This Application Does (Plain-Language Overview)

**Outreach Flow** is a multi-stage sales outreach and sequence management platform designed for revenue teams, founders, and account executives. It automates personalized cold email sequences, detects recipient replies, tracks prospect engagement (email opens and link clicks), and executes multi-channel visual workflows—while using **Google Sheets as its primary cloud database** and **Google Workspace (Gmail API)** as its delivery engine.

### The Core Lifecycle of a Lead
1. **Lead Intake & Ingestion**:
   - Leads enter the system through three methods: manual entry via a single-lead modal, bulk upload using a CSV or Excel (`.xlsx`, `.xls`) file with automated column mapping, or direct synchronization with a connected Google Sheet (`Leads` tab).
   - Each lead is initialized with core profile metadata (name, email, company, job title, LinkedIn URL, industry), personalization context (`painPoint`), a lifecycle status (`Active`), and an initial sequence stage (`0`).

2. **Outreach Sequencing & Multi-Stage Progression**:
   - Outreach follows a standardized 7-stage sequence or a custom node-based visual workflow.
   - The default sequence moves through seven progressive touchpoints:
     - **Stage 1**: Introduction & Pain Point Hook
     - **Stage 2**: Value Proposition & Problem Validation
     - **Stage 3**: Social Proof & Client Case Study
     - **Stage 4**: Solution Deep Dive
     - **Stage 5**: Pricing & ROI Justification
     - **Stage 6**: Gentle Follow-up & Priority Check
     - **Stage 7**: Graceful Break-up
   - Each stage email dynamically interpolates merge tags (e.g., `{{FirstName}}`, `{{Company}}`, `{{PainPoint}}`, `{{SenderName}}`) and injects a 1x1 tracking pixel along with click-tracking redirect URLs.
   - When a stage is dispatched, the system records the Gmail `threadId`. Subsequent follow-up stages are threaded directly into the existing conversation using RFC 2822 `In-Reply-To` and `References` headers, appearing to the prospect as a natural follow-up in the same email thread rather than a disconnected cold message.

3. **Reply Detection & Safety Halts**:
   - Before any email is sent, the system queries the Gmail API thread for that lead. If the prospect has sent a reply message, the outreach sequence is **immediately halted**.
   - The lead's status is automatically updated to `Replied`, their `nextSendDate` is cleared, and they are transitioned to the dedicated **Needs Reply** inbox. This prevents the embarrassing and reputation-damaging scenario of sending an automated follow-up to a prospect who has already responded.

4. **Day-to-Day User Workflow**:
   - **Morning Review**: The operator opens the app and checks the **Needs Reply** tab to handle inbound prospect responses, read thread context, and log outcomes.
   - **Queue Assessment**: The operator checks the **Manual Tasks** dashboard for any human-in-the-loop tasks generated by workflow branches (e.g., "Review LinkedIn profile", "Place direct phone call").
   - **Campaign Execution**: The operator launches the **Campaign Sequencing Runner**, which evaluates all active workflows and leads due for outreach today, enforces sender daily quotas and active time windows, and runs approved batch dispatches.
   - **Analytics & Health Monitoring**: The operator reviews the **Analytics Dashboard** to track delivery funnels, open rates, click-through rates, and reply conversion rates across campaigns.

## 2. How the Pieces Work Together (Architecture Walkthrough)

Outreach Flow is built as a full-stack hybrid web application:
- **Frontend**: Single-Page Application (SPA) built with React 18, TypeScript, Tailwind CSS, Lucide icons, and `@xyflow/react` (ReactFlow v12) for visual workflows.
- **Backend / Proxy**: Node.js Express server (`server.ts`) running on port 3000, serving tracking pixel endpoints, redirect routes, file-parsing services, background execution engines, and local persistence fallbacks.
- **Authoritative Data Layer**: Google Sheets API v4 (remote cloud persistence) with a local JSON disk mirror (`data_store/`) for offline resilience.
- **Dispatch Engine**: Gmail REST API v1 via client-side OAuth Bearer token.

### Execution Trace 1: Sending the Next Sequence Stage (`handleInitiateSendNextStage`)
When an operator clicks **"Send Stage X"** on a lead in the CRM table or lead detail drawer, the following sequential operations take place:

```
[User Clicks "Send Stage X"]
             │
             ▼
[ConfirmationModal Opens] ── (Operator reviews recipient, pain point, and subject preview)
             │
             ▼
[executeSendStageEmail() in src/App.tsx]
             │
             ├──► 1. Pre-Send Reply Safety Check:
             │       Calls checkThreadForLeadReply() in src/services/gmailService.ts
             │       Fetches https://gmail.googleapis.com/gmail/v1/users/me/threads/{threadId}
             │       IF reply detected:
             │          Aborts dispatch immediately.
             │          Updates lead.status = 'Replied'.
             │          Persists update to Google Sheet / local backend.
             │          Alerts operator with a toast warning.
             │
             ├──► 2. Template Rendering & Tracking Injection:
             │       Calls renderEmailMergeTags() in src/data/defaultTemplates.ts
             │       Substitutes {{FirstName}}, {{Company}}, {{PainPoint}}, {{SenderName}}.
             │       Calls wrapLinksAndEmbedTrackingPixel() in src/services/gmailService.ts:
             │         - Wraps <a href="..."> links with http://localhost:3000/api/track/click?...
             │         - Appends <img src="http://localhost:3000/api/track/open?..." width="1" height="1" />
             │
             ├──► 3. MIME Message Construction & RFC 2822 Threading:
             │       Builds MIME headers: To, From, Subject, Content-Type: text/html.
             │       If lead.threadId exists:
             │         Fetches parent message Message-ID header.
             │         Injects In-Reply-To and References headers.
             │         Sets Subject to "Re: <original subject>".
             │       Base64URL encodes the raw email string.
             │
             ├──► 4. Dispatch via Gmail API:
             │       POST https://gmail.googleapis.com/gmail/v1/users/me/messages/send
             │       Headers: Authorization: Bearer <token>
             │       Body: { raw: <encodedBase64>, threadId: <threadId> }
             │       Returns: { id: <messageId>, threadId: <threadId> }
             │
             ├──► 5. Schedule Next Send Date:
             │       Calculates nextSendDate using addBusinessDays(today, gapDays) from src/utils/dateUtils.ts.
             │       Increments lead.currentStage from (X-1) to X.
             │       Updates lead.lastEmailSentDate = today.
             │
             ├──► 6. Data Layer Synchronization:
             │       Calls updateLead() in src/services/leadBackendService.ts.
             │       Writes row update directly to Google Sheets via:
             │         PUT https://sheets.googleapis.com/v4/spreadsheets/{id}/values/Leads!A{row}:W{row}
             │       Mirrors update to Express backend:
             │         POST /api/leads/update -> writes to data_store/leads.json.
             │
             └──► 7. React State Update & UI Notification:
                     Updates leads array state in src/App.tsx.
                     Fires floating green success toast: "Stage X sent to Lead Name via Gmail!".
```

### Execution Trace 2: Automated Campaign Sequencing (`runDueCampaignsJob`)
When an operator runs scheduled campaigns via the **Campaign Sequencing Runner Modal** (`CampaignSchedulerModal.tsx`) or triggers `/api/campaigns/run-due`, execution flows through `server/runnerBackend.ts`:

```
[Operator Clicks "Run Due Campaigns"]
             │
             ▼
[POST /api/campaigns/run-due in server.ts]
             │
             ▼
[runDueCampaignsJob() in server/runnerBackend.ts]
             │
             ├──► 1. Campaign Filtering:
             │       Loads all campaigns from Google Sheets / local storage.
             │       Filters for isActive === true. Inactive campaigns are strictly skipped.
             │
             ├──► 2. Lead Evaluation:
             │       For each active campaign, loads assigned leads.
             │       Skips leads marked Paused, Completed, or Broke Up.
             │       Identifies lead's currentNodeId in the workflow graph.
             │
             ├──► 3. Node Type Execution:
             │       ├── WAIT NODE:
             │       │     Calculates elapsed time (hours/days) against waitDuration.
             │       │     If elapsed, advances lead.currentNodeId along outgoing edge.
             │       │     If not elapsed, leaves lead in waiting state.
             │       │
             │       ├── REPLY CHECK (Safety Priority):
             │       │     Calls checkLeadForReply().
             │       │     If reply detected in Gmail thread, transitions lead.status = 'Replied',
             │       │     halts sequence permanently, and skips send.
             │       │
             │       ├── CONDITION NODE:
             │       │     Evaluates rule (has_replied, email_opened, link_clicked).
             │       │     Branches lead to "yes" or "no" downstream edge.
             │       │
             │       ├── MANUAL TASK NODE:
             │       │     Creates a RunnerManualTask in data_store/tasks.json.
             │       │     Advances lead to downstream node.
             │       │
             │       └── EMAIL SEND NODE:
             │             Checks Sender Quota: sender.sendsToday >= sender.dailySendLimit?
             │               If exceeded -> Postpones send for next day.
             │             Checks Schedule Window: Current day in allowedDays & within startHour/endHour?
             │               If outside window -> Postpones send.
             │             Checks Duplicate Protection: Already sent an email today?
             │               If yes -> Skips send.
             │             Executes Send: Dispatches stage email, increments sender.sendsToday,
             │               updates lead.lastEmailSentDate, advances lead to next node.
             │
             └──► 4. Response & UI Log Rendering:
                     Returns CampaignRunResult: { success, emailsSentCount, tasksCreatedCount, logs }.
                     CampaignSchedulerModal renders execution log stream in real time.
```

## 3. Screen-by-Screen Breakdown

The application interface is organized into a top persistent navigation header, six primary tabs, and five focused workflow modals.

### 1. All Leads View (`tab-leads`)
- **Component File**: `/src/components/LeadsTable.tsx`
- **Purpose**: Central prospect relationship management table.
- **Data Source**: `leads` state array (hydrated from Google Sheets API `Leads` tab or `data_store/leads.json`).
- **User Actions**:
  - Global text search across prospect name, email, company, and notes.
  - Multi-criteria filtering by Lifecycle Status (`Active`, `Replied`, `Paused`, `Completed`, `Broke Up`), Outreach Stage (Stages 0 through 7), and Campaign Name.
  - **Quick Action Buttons**:
    - **Single Stage Send Trigger**: Opens `ConfirmationModal` to review and send the next scheduled stage immediately.
    - **Pause / Resume Toggle**: Halts or resumes automated sequence scheduling for a specific lead.
    - **Delete Lead**: Opens custom `ConfirmationModal` and permanently removes the row from Google Sheets and local storage.
  - **Row Click**: Opens the `LeadDetailModal` drawer for deep conversation history.
  - **Header Actions**: Triggers "Add Single Lead", "Import Leads", "Check Inbound Replies", and "Launch Campaign Scheduler".

### 2. Needs Reply Inbox (`tab-replied`)
- **Component File**: `/src/components/NeedsManualReplyView.tsx`
- **Purpose**: Dedicated priority triage inbox for leads that have replied to outreach.
- **Data Source**: Filtered subset of `leads` where `status === 'Replied'`.
- **User Actions**:
  - Displays conversation snippet, pain point context, company name, and last contact date.
  - **Quick Status Transitions**: Move lead to `Active` (resume sequence), `Paused`, `Completed` (deal closed/won), or `Broke Up` (disqualified).
  - Direct deep-link button to open the active thread in Gmail web interface.
  - Clicking any lead opens the `LeadDetailModal` to inspect the full Gmail message thread.

### 3. Visual Workflow Canvas (`tab-workflows`)
- **Component File**: `/src/components/workflow/WorkflowCanvas.tsx`
- **Purpose**: Drag-and-drop node-based campaign builder powered by ReactFlow.
- **Data Source**: `workflows` state array (stored in Google Sheets `Campaigns` tab and `data_store/campaigns.json`).
- **User Actions**:
  - **Campaign Selector & Tabs**: Switch between campaigns, create blank campaigns from scratch, duplicate existing campaigns, or delete campaigns.
  - **Active / Paused Status Toggle**: Activate or pause campaigns. The automated runner skips all inactive campaigns.
  - **Canvas Node Palette**:
    - **Start Node**: Configure connected sender, allowed sending days (e.g., Monday–Friday), and daily active sending time windows.
    - **Email Node**: Assign sequence stages (1–7) or custom subject line and body text.
    - **Wait Node**: Set delays in business days or hours.
    - **Condition Node**: Branch paths using dual output handles (`Yes` / `No`) based on reply status, email open, link click, or LinkedIn URL presence.
    - **Manual Task Node**: Insert human-in-the-loop tasks (calls, profile reviews) into the sequence.
    - **Merge Node**: Rejoin branching paths into a single downstream sequence.
    - **LinkedIn Invite / Message Nodes**: Placeholder nodes for planned multi-channel sequences.
  - **Interactive Controls**: Drag nodes, connect bezier edges, delete edges via selection or backspace, zoom in/out, pan, toggle minimap, and clear canvas with safety confirmation.
  - **Right-Hand Node Inspector**: Context-sensitive sidebar to edit configuration parameters of the currently selected node.

### 4. Manual Tasks Dashboard (`tab-tasks`)
- **Component File**: `/src/components/ManualTasksDashboard.tsx`
- **Purpose**: Task management queue for human-in-the-loop actions generated by workflow branches.
- **Data Source**: `manualTasks` state array (stored in `data_store/tasks.json` via `/api/tasks`).
- **User Actions**:
  - Filter tasks by status (`Pending` vs. `Completed`) and task type (`Call`, `Review`, `Custom`).
  - View associated prospect name, company, instructions, and target due date.
  - Checkbox toggle to mark tasks as completed.
  - Deep-link button to open the associated lead's profile drawer.

### 5. Stage Templates Admin (`tab-templates`)
- **Component File**: `/src/components/TemplateAdmin.tsx`
- **Purpose**: Authoring and customization environment for sequence email templates.
- **Data Source**: `templates` state array (initialized from `/src/data/defaultTemplates.ts` and persisted to `data_store/settings.json`).
- **User Actions**:
  - Select and edit any of the 7 stages (Stage 1 Intro through Stage 7 Break-up).
  - Customize email subject line and HTML body content.
  - Clickable dynamic merge tag insertion chips: `{{FirstName}}`, `{{LastName}}`, `{{Company}}`, `{{PainPoint}}`, `{{JobTitle}}`, `{{SenderName}}`.
  - Configure default business day wait interval before the subsequent stage.
  - Live side-by-side preview panel showing rendered email against sample lead data.
  - Save all templates to persistent storage.

### 6. Analytics Dashboard (`tab-analytics`)
- **Component File**: `/src/components/AnalyticsDashboard.tsx`
- **Purpose**: High-level KPI reporting and sequence conversion performance.
- **Data Source**: Aggregate statistics calculated from `leads` and raw tracking records from `/api/track/events` (`tracking-events.json`).
- **User Actions**:
  - **KPI Metric Cards**: Total Prospects, Active Leads, Overall Open Rate, Click-Through Rate (CTR), and Reply Rate.
  - **Stage Delivery Funnel**: Bar chart showing how many prospects have progressed through each stage from Stage 1 to Stage 7.
  - **Campaign Performance Breakdown**: Tabular comparison of total leads, sent count, open count, and reply count across campaigns. Clicking a campaign filters the main CRM table.
  - **Real-Time Tracking Event Stream**: Chronological log of recent email opens and link clicks with lead email, stage number, timestamp, and user-agent details.
  - Manual "Refresh Analytics" trigger.

### 7. Lead Detail & Thread Modal (`LeadDetailModal`)
- **Component File**: `/src/components/LeadDetailModal.tsx`
- **Purpose**: Slide-over drawer providing a 360-degree view of a prospect.
- **Data Source**: `selectedLead` object + live Gmail thread fetched via `getGmailThread(token, threadId)`.
- **User Actions**:
  - Edit prospect pain points, notes, company, and job title with immediate sheet persistence.
  - Inspect engagement counters (open count, last opened date, click count, last clicked date).
  - Inspect live Gmail thread: renders sent and received messages, timestamps, and sender avatars.
  - Dispatch the next sequence stage directly from the drawer.
  - Manually pause or resume outreach.
  - Trigger on-demand reply check for this specific lead's thread.
  - Permanently delete the lead.

### 8. Campaign Sequencing Runner Modal (`CampaignSchedulerModal`)
- **Component File**: `/src/components/CampaignSchedulerModal.tsx`
- **Purpose**: Execution engine modal for processing due sequence stages across active campaigns.
- **Data Source**: Active `workflows`, assigned `leads`, `senders`, and `settings`.
- **User Actions**:
  - Filters and displays all leads currently due for an email today based on `nextSendDate`.
  - Validates campaign active status, daily sender quotas, and schedule time windows.
  - Displays a preview of emails ready to be dispatched with recipient name, stage number, and template subject.
  - **"Run Due Campaigns" Button**: Initiates batch execution via `/api/campaigns/run-due` with a real-time terminal-style logging window showing evaluations, wait checks, reply detections, and dispatches.

### 9. Google Sheet Connection Modal (`SheetConnectModal`)
- **Component File**: `/src/components/SheetConnectModal.tsx`
- **Purpose**: Establishes or manages connection to Google Sheets for durable cloud persistence.
- **User Actions**:
  - **Auto-Create New Sheet**: Generates a brand new, pre-formatted Google Spreadsheet in the user's Google Drive with frozen header rows, starter leads, and `Leads` + `Campaigns` tabs via the Google Sheets API.
  - **Connect Existing Sheet**: Input an existing Google Sheet ID or full Google Drive URL.
  - **Disconnect Sheet**: Reverts to local container persistence with a warning about local storage limitations.
  - Displays explicit warning banners regarding local data loss risks if no sheet is connected.

### 10. CSV & Excel Lead Import Modal (`ImportLeadsModal`)
- **Component File**: `/src/components/ImportLeadsModal.tsx`
- **Purpose**: Bulk prospect ingestion engine.
- **User Actions**:
  - Drag-and-drop or file picker for `.csv`, `.xlsx`, and `.xls` files.
  - Automatic column mapping using alias dictionaries (e.g., "E-mail", "Email Address" -> `email`; "Organization", "Firm" -> `company`).
  - Strict email regex validation and malformed record detection.
  - Duplicate detection against existing leads in the system.
  - Interactive preview table of candidate leads before committing.
  - Batch append directly to the connected Google Sheet via `batchCreateLeads`.

### 11. Application Settings Modal (`SettingsModal`)
- **Component File**: `/src/components/SettingsModal.tsx`
- **Purpose**: Operational parameters and white-label branding.
- **User Actions**:
  - **Sequencing Parameters**: Customize default business day gaps between stages (e.g., Stage 1 to 2 = 3 days; Stage 2 to 3 = 4 days) and toggle weekend skipping.
  - **Sender Account Management**: Add, edit, or remove sender profiles, set avatar URLs, toggle primary account, and set daily sending limits (e.g., 150 emails/day).
  - **White-Label Branding**: Customize application title and company logo URL (rendered in the persistent header).

## 5. Integrations & Authentication

Outreach Flow interfaces directly with Google Workspace through official Google APIs.

### 1. Authentication Architecture (Google OAuth 2.0 / Firebase Auth)
- **Token Acquisition**: Authentication is initialized client-side via Firebase Authentication configured with a `GoogleAuthProvider` (`src/services/firebaseAuth.ts`).
- **Scopes Requested**:
  - `https://www.googleapis.com/auth/spreadsheets`: Full read and write access to Google Sheets.
  - `https://www.googleapis.com/auth/gmail.send`: Authorization to dispatch emails on the user's behalf.
  - `https://www.googleapis.com/auth/gmail.readonly`: Authorization to inspect email threads and check for prospect replies.
- **Token Propagation**:
  - On sign-in, the OAuth access token (`accessToken`) is stored in React memory.
  - For client-side Google API operations, it is passed in the HTTP `Authorization: Bearer <token>` header.
  - When communicating with the local Express server (`/api/*`), the token is forwarded in the `Authorization` header so the server can authenticate requests made to Google APIs on the user's behalf.

---

### 2. Google Sheets API v4 Integration
- **Transport**: Direct REST API calls to `https://sheets.googleapis.com/v4/spreadsheets/...`
- **Key Operations**:
  - `POST /v4/spreadsheets`: Creates a new spreadsheet with frozen header rows and pre-seeded starter leads (`createLeadsSpreadsheet`).
  - `GET /v4/spreadsheets/{id}/values/Leads!A1:AA1000`: Reads all lead records and maps 2D cell arrays to typed `Lead[]` objects (`fetchLeads`).
  - `POST /v4/spreadsheets/{id}/values/Leads!A:AA:append?valueInputOption=USER_ENTERED`: Appends new leads or batch imports (`appendLead`, `batchAppendLeads`).
  - `PUT /v4/spreadsheets/{id}/values/Leads!A{row}:AA{row}?valueInputOption=USER_ENTERED`: Surgically updates an existing prospect's row (`updateLeadRow`).
  - `POST /v4/spreadsheets/{id}:batchUpdate`: Issues `deleteDimension` requests to delete rows cleanly without leaving blank gaps (`deleteLead`).
  - `POST /v4/spreadsheets/{id}:batchUpdate`: Issues `addSheet` requests to create the `Campaigns` tab if missing.

---

### 3. Gmail API v1 Integration
- **Transport**: Direct REST API calls to `https://gmail.googleapis.com/gmail/v1/users/me/...`
- **Key Operations**:
  - `GET /profile`: Retrieves the authenticated user's email address to verify identity.
  - `GET /threads/{threadId}?format=full`: Retrieves full conversation history including headers and HTML/text message payloads.
  - `POST /messages/send`: Dispatches outbound emails.
- **Conversation Threading Mechanism**:
  - When Stage 1 is sent, Gmail returns a new `threadId`, which is saved to the lead record.
  - When Stage 2+ is dispatched, `sendStageEmail` fetches the thread from Gmail, extracts the `Message-ID` of the latest message, and sets the RFC 2822 headers:
    ```
    In-Reply-To: <last-message-id>
    References: <all-prior-message-ids>
    Subject: Re: <original-subject>
    ```
  - This ensures all 7 stages appear nested in a single email conversation thread in both the sender's and recipient's email clients.
- **Inbound Reply Detection Algorithm (`checkThreadForLeadReply`)**:
  - Scans all messages in the Gmail thread.
  - Parses the `From:` header using regex to extract the clean sender email address.
  - If any message has a `From` address matching the lead's email, or if `isFromLead` is true and the message timestamp is after the `lastEmailSentDate`, a reply is confirmed.
  - Sequence execution is stopped immediately.

## 6. Current Limitations (Honest Technical Assessment)

To maintain architectural transparency, the following constraints must be understood:

### 1. Email Open and Click Tracking in Development Sandbox
- **Status**: Backend endpoints are fully functional; live recipient inbox tracking is blocked in development.
- **Root Cause**: The endpoints `/api/track/open` and `/api/track/click` are implemented in `server.ts` and successfully write to `tracking-events.json`. However, in the Google AI Studio development container, all external traffic is guarded by a Google session authentication proxy (`/__cookie_check.html`). When an external mail client (e.g., Gmail's image proxy at `googleusercontent.com` or an Apple Mail client) attempts to fetch the 1x1 tracking pixel or follow a tracking link, it lacks the developer's session cookie and receives an authentication redirect or 401 Unauthorized.
- **Production Resolution**: Once the application is deployed to a publicly accessible production URL (such as Cloud Run or a custom domain) without internal cookie-gate proxies, live open and click tracking will function automatically.

### 2. Disconnected Mode vs. Connected Google Sheet
- **Status**: Documented limitation with prominent UI banners.
- **Root Cause**: When a user operates without connecting a Google Sheet, all leads and campaigns are written to local JSON files (`data_store/leads.json`). Because container environments in cloud developer sandboxes can restart, any data created in disconnected mode can be reset to default seed data upon container recreation.
- **Production Resolution**: Connecting a Google Sheet makes Google Drive the permanent, immutable cloud source of truth, immune to local container restarts.

### 3. Missing Autonomous Background Automation (Cron)
- **Status**: Operator-triggered execution.
- **Root Cause**: There is currently no persistent background cron daemon running while the user's browser is closed. The campaign runner (`runDueCampaignsJob`) and reply checker execute when triggered by an operator through the UI (e.g., clicking "Run Due Campaigns" in the scheduler modal or "Check Replies").
- **Production Resolution**: Deploying a server-side cron scheduler (e.g., `node-cron` in `server.ts` or a Cloud Scheduler HTTP trigger to `/api/campaigns/run-due`) would enable autonomous daily morning runs without human intervention.

## 7. What Could Reasonably Be Built Next (Future Features)

These proposed extensions build directly on the existing architecture without requiring structural rewrites:

### 1. Server-Side Autonomous Scheduler (Cloud Cron / `node-cron`)
- **Concept**: Automatically run active campaigns every weekday morning at 8:00 AM recipient local time.
- **Implementation**:
  - Add `node-cron` to `server.ts`.
  - Store a persistent refresh token for the primary sender account.
  - Trigger `runDueCampaignsJob()` on a cron schedule (`0 8 * * 1-5`), logging results to `data_store/runner-logs.json`.
  - Send an executive summary email to the operator with the number of emails sent and replies detected.

### 2. AI-Assisted Cold Email Personalization (Gemini API)
- **Concept**: Dynamically generate personalized opening sentences and conversation hooks based on the prospect's company, industry, and LinkedIn profile summary.
- **Implementation**:
  - The project already has `@google/genai` declared in server dependencies and includes `MAJOR_CAPABILITY_SERVER_SIDE_GEMINI_API` in `metadata.json`.
  - Create a new server route: `POST /api/ai/personalize-lead`.
  - In `LeadDetailModal.tsx` and `TemplateAdmin.tsx`, add an "AI Personalize" button that invokes Gemini 2.5 Flash to generate tailored hooks based on `lead.painPoint`, `lead.company`, and `lead.industry`.

### 3. A/B Variant Testing for Stage Templates
- **Concept**: Split-test different subject lines and value propositions within any sequence stage to identify higher-converting copy.
- **Implementation**:
  - Update `StageTemplate` in `src/types.ts` to include `variants: { id: string; subject: string; bodyHtml: string; weight: number }[]`.
  - In `server/runnerBackend.ts`, implement weighted random selection when dispatching emails.
  - In `AnalyticsDashboard.tsx`, display comparative open and reply conversion metrics per variant.

### 4. Direct CSV Export & Google Sheet Bi-Directional Webhooks
- **Concept**: Allow operators to export filtered views to CSV directly from the CRM table, and register Google Apps Script webhooks to update Outreach Flow instantly when an external user edits the Google Sheet.
- **Implementation**:
  - Add client-side CSV export utility in `src/components/LeadsTable.tsx`.
  - Expose an unauthenticated webhook route `POST /api/webhooks/sheet-update` secured by a shared secret token to invalidate and refresh the server-side lead cache.
